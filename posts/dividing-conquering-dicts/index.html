Dividing and Conquering Nested Dictionaries

August 16, 2024 - 6 minutes read - 1131 words

The Problem

This should be a short one1. I’ve noticed a few times over my last couple of jobs the desire to use dictionaries for things like configuration or representing objects that you’re not yet committed to putting into a class. For example:

input_configuration = {
    "data": {
        "root_directory": "/path/to/the/directory",
        "data_format": "csv",
        "dataset": {
            "feature_weights": None,
            "categorical_features": ["a"],
        },
        "loader": {
            "strategy": {
                "name": "tiled",
                "num_tiles": 4,
                "tiling": {
                    "name": "columnar",
                    "columns": ["a", "b", "c"],
                },
            },
        },
    },
    "sampling": {
        "strategy": {
            "name": "k-fold cross-validation",
            "k": 5,
        },
    },
    "model_lib": "lgbm",
    "model_spec": {
        "objective": "auc",
        "num_leaves": 512,
        "categorical_feature_encoding": "one-hot",
    },
}

This is usually fine, ish, for small codebases.

However!

It is very (very) easy to spiral out of control and end up with a leviathian monstrosity that is a massive pain to maintain and understand. In particular, I’ve noticed you are at risk of something like this happening:

def some_func():
    input_config = get_input_configuration()
    # Change fields at will. Or set defaults several functions later.
    # This definitely makes things clearer.
    input_config["sampling"]["strategy"]["k"] = 10
    # Why not just add new fields when you feel like it?
    input_config["plot"] = update_plot(input_config)
    # Why not make it vague for less experienced programmers whether
    # it's keys, values, or items you're iterating over? (It's keys,
    # by the way.)
    for param in input_config["data"]:
        # Branching galore!
        if param == "dataset":
            do_something_with_dataset(...)
        # Don't forget how concise nested fields are! Especially with
        # code that doesn't know if they're in there or not.
        # And unlike class fields, typos are a concern too...
        if key_in_dict(input_config, ...):
            input_config["daat"]["loadre"]["startegy"]["n_tiles"] = max(
                input_config["data"]["loader"]["strategy"]["num_tiles"],
                ...
            )

Simply put, the dictionary becomes very stateful, and hard to understand. As it evolves over time, the effective ‘version’ is changing, without any single source of truth or reference to say “this is what can be there, and nothing else”. Accessing nested keys is verbose, and flattening the dictionary isn’t a great option either. Although filter(), map(), and merge()2 are easier to apply, nesting structure can be useful for separation of concerns.

The Solution

Now obviously using a class or type addresses most or all of these issues quite straightforwardly. You also get a bunch of other benefits as well, namely:

  • Type safety.
  • Standard tools for things like equality comparisons.
  • Field accesses can’t have typos (a surprisingly easy bug to miss, it seems).

With that being said, sometimes having a dictionary is the right abstraction to use! Because Python dictionaries are iterables, things like filter(), map(), and merge() are available straight out of the box. Further, you may either be dealing with libraries that use dictionaries (or JSON) themselves, like Vega does. The reason they do so is because there are absolutely loads of options and settings that are liable to change, making a dictionary the sensible choice. Finally, moving towards classes isn’t necessarily a binary step - sometimes it makes sense to make more incremental steps as part of larger-scale refactoring. Just because it was the right thing to do in hindsight, doesn’t automatically make it the best thing to do in the present.

Instead, I am quite fond of what I regard as a very mathematical way of solving the problem using divide-and-conquer. You have a reference dictionary with default values, you have your input, you flatten both, do some operations like filter(), merge() the results, and nest the resultant dictionary.

I do this via hand-rolled flatten() and nest() functions respectively:

def flatten(d: dict, separator: str = ":", stem: str = "") -> dict:
    """
    Flatten `d` such that no value is a dict - other iterables are
    unaffected.
    """
    result = {}
    for key, value in d.items():
        if isinstance(value, dict):
            sub_dict = flatten(d[key], stem=stem+key+separator)
            # This should be safe. If it isn't, someone has chosen
            # some *really* bad keys.
            result = result | sub_dict
        else:
            result[stem+key] = value
    return result


def nest(d: dict, separator: str = ":") -> dict:
    """
    Nest `d` such that every nested key is fully expanded, and all
    implied sub-dicts are recovered.
    """
    result = {}
    for key, value in d.items():
        # This works because we are getting a *reference*, not a
        # copy! This means we can iterate to the end of a given
        # nested key and set the value without worrying about
        # dropping everything else.
        current = result
        tokens = key.split(separator)
        for token in tokens[:-1]:
            if token not in current:
                current[token] = {}
            current = current[token]
        current[tokens[-1]] = value
    return result

# >>> original = {"foo": 1, "bar": 2, "baz": {"qux": 3, "quux": 4}}
# >>> nest(flatten(original)) == original
# True

And correspondingly, use them like so:

def some_func():
    input_config = get_input_configuration()
    reference_config = get_ref_configuration_with_defaults()

    flat_input = flatten(input_config)
    flat_ref = flatten(reference_config)
    # This generalises - we can have multiple reference dictionaries.

    # Eliminate any keys not in the reference dictionary.
    in_flat_ref = lambda pair: pair[0] in flat_ref.keys()
    filtered_input = dict(filter(in_flat_ref, flat_input.items()))

    do_some_stuff_if_needed(filtered_input)
    # Have flat_ref be first, so that the input takes precedence.
    merged_result = {**flat_ref, **filtered_input}
    return nest(merged_result)

This order of operations guarantees:

  • The result will have all and only the keys specified in your reference dictionary.
  • Each key specified in your transformed dictionary will always have a value.
  • Your input will override the reference dictionary where they conflict.

In my opinion this is a really nice solution. You have something as a reference that you can more easily check in your git history, you can reason about what’s in the dictionary, you know that defaults are present, and the change is more incremental - meaning you can shuffle code into get_ref_configuration_with_defaults() over time. This last point is underrated, in my view - you can get some of the benefits and less development cost like you’d get with jumping straight to classes. And the ensuing burning of your test suite as you faff around trying to hunt down every last bug.

But it also makes transitioning to a class or other abstraction much easier, since you can then just replace the return types with classes, having separated the type change from the other organisational changes. flatten() and nest() are fairly simple primitives that can potentially be used for other purposes as well, along with surprising use-cases - in one of my previous roles I had originally dealt with a huge configuration loading process with this solution. But because the library I was working with also interacted with Vega, I found myself re-using the same solution and ended up cutting down the amount of code for each new visualiation by half3.

And then, hopefully, you can start using types and forget about all of this.
